# CI/CD Pipeline Performance Optimization — End-to-End Build Plan

**Project type:** BITS Pilani WILP Dissertation / Project Work (carried out at Wipro)
**Deliverable for the agent:** a working, measurable, reproducible optimization of a realistic CI/CD pipeline, plus the evidence (raw data, charts, report) needed for the dissertation.

This document is the spec an Opus agent should build from. It makes every technology decision up front so the agent can execute without re-deciding. Read `CLAUDE.md` (working rules) before starting.

---

## 0. One-paragraph summary

We build a realistic polyglot monorepo that resembles a typical Wipro enterprise engagement (Java Spring Boot API + React/TypeScript web app + Python analytics service + a shared library), give it a deliberately conventional "legacy" CI pipeline (single sequential job, no caching, runs every test, builds every image on every push), and then **profile it**, **optimize it in four measured steps** (dependency and Docker layer caching → DAG parallelization and duration-balanced test sharding → test impact analysis → ephemeral autoscaled runners), and **prove the gains** with a paired experiment in which the same 30 commits are run through the baseline and the optimized pipelines. We ship three reusable tools (a CI profiler, a test-impact-analysis selector, a duration-based sharder), an ephemeral-runner setup, a results dashboard, and a portability playbook that maps every technique onto Jenkins, Azure DevOps and GitLab CI, which is what Wipro projects actually run.

---

## 1. Why this project is a good dissertation

- **Measurable:** every claim is a number from the CI provider's own API (durations, queue time, billable minutes). No subjective evaluation needed.
- **Real engineering, not a toy:** caching, DAG scheduling, test selection, runner autoscaling are exactly what platform/DevOps teams at Wipro do for clients.
- **Research hooks:** test impact analysis (regression test selection) has a 30-year literature; CI build duration has recent empirical studies. Easy to write a literature review and compare our results.
- **Low cost:** GitHub Actions is free for public repos (and 2000 min/month for private); ephemeral runners can run on the student's laptop via a local Kubernetes cluster, with cloud cost *modeled* from published prices and optionally validated on a small cloud VM.

## 2. Fixed technology decisions

| Concern | Decision | Why |
|---|---|---|
| CI platform | **GitHub Actions** | Free, rich REST API for run/job/step timings, native caching, matrix jobs, self-hosted runner support. Portability playbook covers Jenkins/ADO/GitLab. |
| Repo visibility | **Public** repo named `wipro-cicd-optimization` | Unlimited hosted minutes. Self-hosted jobs restricted to `push` events by the owner (never fork PRs) to stay safe. |
| Reference workload | Monorepo **"RetailOps"**: `apps/orders-api` (Java 21, Spring Boot 3, Maven, JUnit 5, Testcontainers+Postgres), `apps/web` (React 18, TypeScript, Vite, Vitest, Playwright), `apps/analytics` (Python 3.12, FastAPI, pytest), `libs/shared-schemas` (JSON Schema → generated TS + Java + Python types, so a shared change impacts all three services) | Polyglot = three different caching strategies and three test frameworks; shared lib = realistic cross-service impact for TIA. |
| Test volume | ~400 JUnit tests (incl. ~40 Testcontainers integration tests), ~600 Vitest tests, ~30 Playwright e2e, ~500 pytest tests. Tests may be generated from templates but must be real, passing tests that exercise real code. | Baseline must be slow enough (target 20–30 min sequential) that optimizations are visible and statistically clear. |
| Containers | Docker multi-stage builds for all three services, pushed to GHCR | Docker layer caching is one of the biggest wins and must be demonstrated. |
| Profiler | **`cipro`** (Python 3.12 CLI, standard library only; Plotly.js via CDN in the HTML report; see ADR-0004) | Pulls runs/jobs/steps from GitHub API into SQLite, computes metrics, renders HTML reports. Reusable on any GitHub repo (and any Wipro client repo). |
| TIA tool | **`tia`** (Python CLI) | Hybrid: static dependency graph (fast, always available) + dynamic per-test coverage map (built nightly) + safety rules. Framework adapters for JUnit, Vitest, pytest. |
| Sharder | **`shardkit`** (Python CLI) | Greedy bin-packing of test files/classes into N shards using historical durations from JUnit XML. |
| Ephemeral runners | **Actions Runner Controller (ARC), runner-scale-set mode**, on a local **k3d** cluster (Docker Desktop/WSL2), with a custom warm runner image. Optional validation on one cloud VM. | Industry standard, scales to zero, no inbound webhooks needed (long-polls GitHub). |
| Dashboard | Static HTML (Plotly) generated by `cipro report`, published via GitHub Pages | Zero infra, shareable link for the examiner. |
| Experiment design | **Paired replay**: 30 curated commits pushed to `exp/*` branches; both `ci-baseline.yml` and `ci-optimized.yml` trigger on the same push | Removes commit-to-commit variance; identical inputs → clean before/after. |
| Local workflow testing | `nektos/act` for syntax/smoke only; real timings always from GitHub | act timings are not representative. |

Prerequisites on the Windows host: Git, GitHub CLI (`gh`), Docker Desktop with WSL2 backend, Java 21 (Temurin), Maven 3.9, Node 20 LTS, Python 3.12, `k3d`, `kubectl`, `helm`. The agent should install missing tools via `winget` and verify versions in Phase 0.

## 4. Phases, deliverables and acceptance criteria

Each phase ends with: a git tag, a `docs/phase-results/phase-N-results.md` containing raw numbers and the exact commands that produced them, and a short ADR for any non-obvious decision. **No phase is "done" until its acceptance criteria are met with real data from GitHub.**

### Phase 0 — Workload and baseline pipeline (the "legacy Wipro pipeline")

**Build**
1. Scaffold the three apps and the shared lib. Each must have real business logic (orders CRUD + pricing rules; web pages for order list/detail/create; analytics endpoints computing aggregates) so tests are meaningful.
2. Generate the test suites to reach the target counts. Tests must pass, be deterministic, and have realistic duration distributions (a few slow integration tests, many fast unit tests). Record counts in the phase results.
3. Dockerfiles (multi-stage) for all three apps; `docker compose` for local run.
4. `ci-baseline.yml`: one job, `ubuntu-latest`, triggered on push to `main` and `exp/**`. Steps in order: checkout → install Java/Node/Python → build shared-schemas → `mvn verify` → `npm ci && npm test && npx playwright test` → `pip install && pytest` → build all three Docker images → push to GHCR. **No cache actions, no matrix, no path filters.** This is intentionally how many real enterprise pipelines look.
5. Run the baseline 10 times on `main` (empty commits are fine) to get a first duration distribution.

**Acceptance**
- Baseline runs green 10/10.
- p50 duration ≥ 18 min (if lower, add realistic weight: more integration tests, heavier e2e, bigger images; document what you added).
- Tag `baseline-v1`. From this point `ci-baseline.yml` is never edited except for pure bug fixes, recorded in an ADR.

### Phase 1 — Profiler (`cipro`) and baseline report

**Build**
1. `cipro fetch --repo <o/r> --workflow ci-baseline.yml --last 50` → stores runs, jobs, steps (with `started_at`/`completed_at`), runner labels, conclusion, and `billable` minutes (from the run timing endpoint) into SQLite.
2. `cipro logs` → downloads job logs and extracts cache events (`Cache restored from key`, `Cache not found`, `Cache saved`) and test counts (parse surefire/vitest/pytest summaries).
3. `cipro report --out docs/dashboard/` → HTML with: per-run Gantt (jobs/steps), **critical path**, step-level p50/p95 table, **waste breakdown** (setup+install vs build vs test vs publish), queue time, cache hit rate, billable minutes, modeled cost.
4. `cipro compare --a ci-baseline.yml --b ci-optimized.yml --since <tag>` → paired comparison table and charts.
5. Cost model in `tools/cipro/src/cipro/pricing.toml` with GitHub-hosted per-minute rates by runner size and cloud spot prices for self-hosted estimates. **Verify current prices at build time and cite the source URL + date in the file.**

**Acceptance**
- `cipro report` on the 10+ baseline runs produces a dashboard; the waste breakdown shows where time goes (expect: dependency install + Docker builds dominate).
- `docs/phase-results/phase-1-results.md` has the baseline table: p50, p95, billable min/run, cost/run, % time in setup.
- `cipro` has unit tests (≥ 80% coverage) and works against an arbitrary public repo (test on one well-known open-source repo as a smoke test).

### Phase 2 — Caching (one PR per cache type, each measured)

**Build (in this order, each its own PR with before/after from `cipro compare`)**
1. Maven: `actions/cache` on `~/.m2/repository` keyed by `**/pom.xml` hash; `-o` offline flag when restored.
2. npm: `actions/setup-node` built-in cache + Playwright browser cache keyed by Playwright version.
3. pip: `actions/setup-python` cache keyed by lock file.
4. Docker: `docker/build-push-action` with BuildKit `cache-from/cache-to type=gha` (fallback: registry cache in GHCR). Reorder Dockerfiles so dependency layers come before source copy.
5. Build outputs: Maven incremental via build cache (if time permits; otherwise skip and note), Vite build cache.

**Acceptance**
- Cache hit rate ≥ 90% on warm runs (from `cipro logs`).
- Report time saved per cache type separately. Expected: Docker + Maven are the big ones.
- Tag `opt-cache-v1`.

### Phase 3 — Parallelization and duration-balanced sharding

**Build**
1. Restructure `ci-optimized.yml` into a DAG: `changes` (path filter) → fan-out jobs `lint`, `unit-java`, `unit-web`, `unit-py`, `integration-java`, `e2e-web`, `build-images` (matrix over 3 apps) → `publish`. Use `needs:` only where a real dependency exists.
2. `concurrency: cancel-in-progress` per branch; `timeout-minutes` on every job; `fail-fast: false` on test matrices so one shard's failure doesn't hide others.
3. `shardkit`: reads test durations from JUnit XML (Maven surefire, Vitest `--reporter=junit`, pytest `--junitxml`) stored by `nightly-full.yml` as a workflow artifact (and committed snapshot in `experiments/durations/` for reproducibility). `shardkit plan --shards N --framework junit` outputs the include list for shard i. Falls back to round-robin if no history.
4. Shard the three unit suites and e2e (start with 4 shards each; tune by measuring wall-clock vs billable minutes trade-off and report the curve).
5. Playwright: run with `--shard=i/N` plus `shardkit` ordering; reuse the built `web` artifact instead of rebuilding.

**Acceptance**
- Wall-clock p50 of `ci-optimized.yml` ≤ 40% of baseline on the same commits.
- A chart showing wall-clock and billable minutes vs. number of shards (1, 2, 4, 8) — this is the cost/speed trade-off the dissertation discusses.
- Shard imbalance (max shard time − min shard time) with `shardkit` vs naive round-robin, reported.
- Tag `opt-parallel-v1`.

### Phase 4 — Test Impact Analysis (`tia`)

**Build**
1. **Static layer:** per framework, build the import/dependency graph of test → source. Java: parse imports + Maven module graph (use `jdeps` on compiled classes for accuracy). TS: use the TypeScript compiler API or `madge` for the import graph. Python: `modulegraph`-style AST import parsing. Shared-schemas changes map to all generated consumers.
2. **Dynamic layer (nightly):** `nightly-full.yml` runs the whole suite with per-test coverage: JaCoCo with per-test-class sessions (or a surefire listener that dumps per-class exec data), Vitest `--coverage` per test file (run per-file in CI nightly; cost is acceptable nightly), pytest + `coverage` with `dynamic_context = test_function`. Produce `coverage-map.json`: `source_file → [tests]`. Publish as artifact and commit a snapshot.
3. **Selector:** `tia select --base <sha> --head <sha>` → changed files (git diff) → union of static and dynamic mappings → plus **safety rules**: (a) always-run smoke set per app, (b) changes to build files, CI files, Dockerfiles, lockfiles, or the shared lib's codegen templates → run **full** suite for affected app(s), (c) if coverage map older than 7 days or missing → fall back to static only and widen by one dependency hop, (d) PRs run selected set; `main` and nightly always run full suite (safety net).
4. Integrate into `ci-optimized.yml` on PR/exp branches: each test job runs `tia select` and passes the include list to the framework.
5. **Safety evaluation (this is the key research result):**
   - *Agreement study:* over the 30 replay commits, the full suite is also run; report whether the TIA-selected subset fails iff the full suite fails (confusion matrix, recall of failing tests).
   - *Fault injection:* script that creates 60 synthetic bugs (20 per language: flipped conditions, off-by-one, removed null checks, changed constants) in random source files, each as a separate commit; report how many are caught by the TIA-selected set vs full suite. Target recall ≥ 98%; report every miss and why.
   - Compare static-only vs hybrid selection to show why the dynamic map matters.

**Acceptance**
- Median % of tests executed on the 30 replay commits (expect 10–40% depending on category) reported per category (frontend-only, backend-only, shared-lib, docs-only, config).
- Fault-injection recall ≥ 98%, misses explained, and the safety rules updated if a systematic miss is found.
- Tag `opt-tia-v1`.

### Phase 5 — Ephemeral autoscaled runners

**Build**
1. `infra/runner-image/Dockerfile`: based on the ARC runner image, pre-installed Java 21, Maven, Node 20, Python 3.12, Playwright browsers, Docker CLI, with the Maven/npm/pip caches **pre-warmed** at image build time. Rebuilt weekly by a workflow.
2. `k3d` cluster config; ARC installed via Helm in runner-scale-set mode with `minRunners: 0`, `maxRunners: 6`, ephemeral (one job per pod). Docker-in-Docker or Kaniko for image builds inside the pod (choose DinD for simplicity; note the security trade-off in an ADR).
3. `ci-ephemeral.yml`: identical to `ci-optimized.yml` but `runs-on: [self-hosted, arc-retailops]`, restricted to `push` events from the repo owner. Never run fork PRs on self-hosted runners.
4. Measurement: queue time, pod cold-start time, job duration, pod CPU-seconds and memory (from `kubectl top` / metrics-server scraped by a small sidecar script into `experiments/results/`). Model cost = CPU-seconds × spot price of a comparable VM (cite price source and date) + control-plane amortization. Compare with GitHub-hosted billable minutes × per-minute rate.
5. Stretch: run the same scale set on one cloud spot VM (AWS/Azure/GCP free credits) for a day and record the actual bill as validation of the model. **Ask the user before spending any money.**

**Acceptance**
- Paired comparison hosted vs ephemeral on at least 15 replay commits: wall-clock, queue time, cost per run.
- Scale-to-zero demonstrated (pods = 0 when idle, screenshot + `kubectl` output in results).
- Tag `opt-ephemeral-v1`.

### Phase 6 — Controlled experiment and analysis

**Build**
1. `experiments/commits/manifest.yaml`: 30 commits across 6 categories × 5 each: frontend-only, backend-only, analytics-only, shared-lib (touches all), docs-only, config/CI change. Each is a stored patch generated from real edits (not random bytes).
2. `scripts/replay.py`: for each commit, create `exp/<n>` branch from `main`, apply patch, push; both `ci-baseline.yml` and `ci-optimized.yml` (and `ci-ephemeral.yml` when the cluster is up) run on it. Interleave categories and run across at least two different days/times to spread provider variance. Repeat the whole set twice if budget allows.
3. `cipro fetch` everything; `cipro compare` produces the headline tables and charts; notebooks compute confidence intervals (bootstrap) on p50/p95 differences.
4. Headline metrics table (all with CI):

5. Threats to validity section: synthetic workload, GitHub-hosted variance, laptop-based runner cost modeled not billed, generated tests.

### Phase 7 — Portability playbook and dissertation artifacts

**Build**

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Baseline too fast to show gains | Add realistic weight (integration tests, e2e, image size) in Phase 0; document additions honestly. |
| GitHub-hosted runner variance hides effects | Paired design, 30 commits, interleaving across days, bootstrap CIs. |
| TIA misses a real failure | Safety rules + full suite on `main`/nightly; fault-injection study quantifies risk instead of hiding it. |
| ARC on laptop k3d flaky (DinD, resources) | Cap `maxRunners` at what the laptop supports; Kaniko fallback; stretch cloud VM. |
| Self-hosted runner security on a public repo | Only `push` events from owner; no fork PRs on self-hosted; document in ADR. |
| Hosted minutes exhausted (if repo made private) | Keep public; or move baseline reruns to self-hosted after Phase 5. |
| Generated tests look artificial to examiner | Tests exercise real logic; distribution of durations reported; limitation stated in Threats to Validity. |
| Scope creep | Phases 0–4 + 6 are the minimum; everything else is explicitly optional. |
