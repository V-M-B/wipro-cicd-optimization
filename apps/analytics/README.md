# analytics — RetailOps sales analytics service

Python 3.12 FastAPI service that computes retail sales analytics over the shared
RetailOps schemas (`app/generated/schemas.py`, generated by
`libs/shared-schemas/codegen.py` — do not edit). All computation is pure Python
standard library (no pandas/numpy) so the image stays small and every number is
traceable to plain code.

## Layout

| Path | Purpose |
|---|---|
| `app/datasets.py` | Deterministic synthetic data generator (`DatasetConfig` → customers, products, orders). One seeded `random.Random`; dates are injected, never read from the clock. |
| `app/metrics/common.py` | Periods (day / ISO week / month), status sets, order-total allocation over lines, rounding. |
| `app/metrics/revenue.py` | Revenue total/gross/discount, by period, region, tier, category; AOV (overall, by region); coupon usage. |
| `app/metrics/products.py` | Per-SKU sales, top-N, ABC (Pareto) classes, basket co-occurrence, affinity rules (support / confidence / lift). |
| `app/metrics/customers.py` | RFM quintile scores and segments, cohort retention matrix (`active` and `rolling`), churn flags, retention-based CLV. |
| `app/metrics/timeseries.py` | SMA, WMA, exponential smoothing, Holt linear, pct change, week-over-week, z-score / IQR / rolling z-score anomalies. |
| `app/metrics/funnel.py` | CREATED → PAID → SHIPPED → DELIVERED funnel, cancellation rate, bottleneck, by region / period. |
| `app/io/csv_io.py` | CSV import/export for customers, products, orders with row-level validation errors. |
| `app/api.py`, `app/api_models.py` | FastAPI app and request bodies. |

Metric conventions:
- **Revenue** counts orders in `PAID`, `SHIPPED`, `DELIVERED` and uses `Order.total` (after coupons).
  Line-level breakdowns (category, product) split each order total over its lines in proportion to
  gross line value, so every breakdown reconciles with the total.
- **Activity** (retention, churn) counts every status except `CANCELLED`.
- **Funnel**: `status` is the current state; a `DELIVERED` order passed every earlier stage.
  `CANCELLED` orders are assumed cancelled before payment (they reach `CREATED` only).
- Everything time-dependent takes an explicit `as_of` / `end` date.

## Endpoints

| Method | Path | Body / query |
|---|---|---|
| GET | `/health` | — |
| GET | `/demo` | `seed`, `n_orders` (≤ 20000), `n_customers`, `n_products`, `start`, `end` → dashboard summary of a generated dataset |
| POST | `/revenue/summary`, `/revenue/by-period`, `/revenue/by-region`, `/revenue/by-category`, `/revenue/aov` | `{orders, customers?, products?, granularity?, fill_gaps?}` |
| POST | `/revenue/coupons` | `{orders}` |
| POST | `/products/top` | `{orders, products?, n?, by?: revenue\|units\|orders}` |
| POST | `/products/abc` | `{orders, products?, a?, b?}` |
| POST | `/products/affinity` | `{orders, min_support?, min_confidence?, limit?}` |
| POST | `/customers/rfm` | `{orders, as_of}` |
| POST | `/customers/retention` | `{orders, mode?: active\|rolling, end?}` |
| POST | `/customers/churn` | `{orders, as_of, threshold_days?}` |
| POST | `/customers/clv` | `{orders, as_of, gross_margin?, retention?, discount_rate?}` |
| POST | `/timeseries/smooth` | `{values, method?: sma\|wma\|ema\|holt, window?, alpha?, beta?, horizon?}` |
| POST | `/timeseries/anomalies` | `{values, method?: zscore\|iqr\|rolling, threshold?, k?, window?}` |
| POST | `/timeseries/week-over-week` | `{orders}` |
| POST | `/funnel` | `{orders, customers?, by_region?}` |
| POST | `/csv/{customers,products,orders}/validate` | `{content: "<csv text>"}` |

`orders`, `customers`, `products` are lists of the generated `Order`, `Customer`, `Product` models.
Invalid metric parameters return HTTP 422 with `{"detail": "..."}`. OpenAPI docs: `/docs`.

## Adding a metric

1. Put the computation in the matching `app/metrics/*.py` module as a pure function over the
   generated models. Reuse `app/metrics/common.py` for periods, status sets, allocation and `money()`
   rounding instead of re-implementing them. Raise `ValueError` for invalid parameters; the API turns
   it into HTTP 422.
2. Take time as an argument (`as_of`, `end`); never read the clock.
3. Add hand-checked tests in `tests/metrics/` against `tests/factories.py` (`tiny_orders()` documents
   its expected values). Add a `*_large.py` test marked `@pytest.mark.slow` only for scale invariants.
4. If the metric is exposed over HTTP: add the request model to `app/api_models.py`, the route to the
   router in `app/api.py`, an API test in `tests/api/`, and a row to the endpoint table above.
5. Run `ruff check .` and `pytest` before pushing.

## Commands

```bash
# from apps/analytics
python -m venv .venv
# Windows: .venv\Scripts\activate     POSIX: source .venv/bin/activate
pip install -r requirements-dev.txt
ruff check .
pytest --junitxml=reports/junit.xml           # full suite (default command)
pytest -m "not slow"                          # fast unit/API tests only
pytest -m slow                                # data-heavy tests only
pytest --cov=app --cov-context=test           # per-test coverage contexts (for TIA)
uvicorn app.api:app --reload                  # run locally on :8000

# from the repository root
docker build -t analytics:local apps/analytics
docker run --rm -p 8000:8000 analytics:local
```

The `Dockerfile` is the intentionally naive Phase 0 baseline: `COPY . .` before
`pip install`, so any source change invalidates the dependency layer.

## Test suite

Counts from `reports/junit.xml` of a local run (Windows 11, Python 3.13.5, 2026-10-25):

| | Tests | Sum of test times |
|---|---:|---:|
| `@pytest.mark.slow` (8 `*_large.py` modules) | 45 | 37.00 s |
| other (25 modules) | 570 | 1.98 s |
| **total** (33 modules) | **615** | 40.67 s (JUnit suite time) |

Wall clock for `pytest --junitxml=reports/junit.xml`: 42.4 s (pytest reported 40.74 s); an earlier
run on the same machine took 52.4 s wall (50.18 s reported), so expect roughly ±25 % run-to-run variance.
Fast subset under `--cov=app --cov-context=test`: 570 tests in 16.85 s, 99 % line coverage of `app/`.

- Fast tests assert hand-computed values over a small hand-made dataset (`tests/factories.py`,
  values documented in `tiny_orders()`), plus `@pytest.mark.parametrize` tables and property checks
  on small/medium generated datasets (600 and 4,000 orders, session-scoped in `tests/conftest.py`).
- Slow tests (`*_large.py`) generate their own 20k–100k-order dataset per module (module-scoped
  fixture, so each module pays its own generation cost and modules shard independently) and assert
  invariants: breakdowns reconcile with totals, monthly = Σ daily, retention matrix triangular with
  `rolling` non-increasing and ≥ `active`, ABC partition shares, affinity consistent with
  co-occurrence counts, injected spikes detected, CSV round trips at scale, API results equal library
  results. Slowness comes only from real computation and data generation; there are no sleeps.
- **Generated tests: none.** No generator script was needed; every test and parametrize table is
  hand-written (`scripts/` is not used).
- Deterministic: seeded `random.Random` only, no network, no wall clock (`as_of` dates are fixed).
  Warnings are errors (`filterwarnings = error`), except Starlette's deprecation notice for using
  `httpx` with `TestClient` (Starlette ≥ 1.x recommends `httpx2`; `httpx` is the dependency fixed by
  the project plan).

Timings above were measured once on the author's machine and are not CI numbers; CI durations come
from the pipeline runs collected by `cipro`.
